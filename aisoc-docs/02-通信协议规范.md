# 02 通信协议规范

> 版本 v0.1 ｜ 2026-08-13
> 上游：计划书 3.3。本文是平台地基，**所有大脑/部件必须遵守，谁也不许自说自话**。

---

## 1. 协议总览

三张核心数据表 + 一条事件流：

| 协议 | 方向 | 用途 |
|---|---|---|
| TaskMessage | 大脑 → 部件 | 任务下发 |
| Finding | 部件 → 大脑 | 证据上报 |
| Report | 大脑 → 用户 | 报告输出（部件也可产草稿） |
| SSE 事件流 | 部件 → 大脑 | 流式输出/审批请求/进度 |

**传输**：HTTP REST（JSON）+ SSE。所有请求 `Content-Type: application/json`。

---

## 2. TaskMessage（任务下发）

```json
{
  "task_id": "T20260813-0001",
  "domain": "pentest",
  "target": "http://10.0.0.5",
  "params": {
    "scope": "port_scan,dns_enum",
    "timeout_s": 600,
    "max_steps": 20
  },
  "tools": ["port_scan", "dns_enum", "cve_search"],
  "context": {
    "ref_task_ids": ["T20260813-0000"],
    "evidence_summary": "审计发现 10.0.0.5 在 21:00-22:00 有异常爆破行为"
  },
  "auth": "tk_pentest_..."
}
```

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `task_id` | ✅ | string | 全局唯一，`T+YYYYMMDD-序号`，贯穿全链路 |
| `domain` | ✅ | enum | 路由依据：`pentest` / `logaudit` / `threatintel` / `incident` |
| `target` | ✅ | string | 目标 IP/域名/URL，**必须在授权白名单内**（见 06） |
| `params` | ❌ | object | 参数（scope / timeout / max_steps 等） |
| `tools` | ❌ | string[] | 可用工具白名单，缺省=该部件全部工具 |
| `context` | ❌ | object | 跨域上下文：来源任务引用 + 证据摘要（星型协作的载体） |
| `auth` | ✅ | string | 部件实例 token（注册表下发，防伪造） |

**下发方式**：大脑 `POST http://127.0.0.1:<port>/submit`，body 即 TaskMessage（reasonix serve 接受 `{"input": ...}`，大脑需将 TaskMessage 序列化为部件的 input 文本，见 6 节映射）。

## 3. Finding（证据上报）

```json
{
  "id": "F-T20260813-0001-001",
  "task_id": "T20260813-0001",
  "domain": "pentest",
  "target": "http://10.0.0.5",
  "tool": "port_scan",
  "severity": "high",
  "cve": "CVE-2021-44228",
  "cwe": "CWE-502",
  "cvss": 10.0,
  "title": "目标暴露 Log4j 组件",
  "description": "80 端口服务含 Log4Shell 受影响组件",
  "evidence": "port_scan 输出：443/tcp open https ...",
  "remediation": "升级 log4j 至 2.17.1+",
  "confidence": 0.92,
  "mitre": ["T1190", "T0869"],
  "timestamp": "2026-08-13T10:00:00Z"
}
```

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `id` | ✅ | string | 唯一：`F-<task_id>-<seq>` |
| `task_id` | ✅ | string | 来源任务 |
| `domain` | ✅ | enum | 产出部件 |
| `target` | ✅ | string | 目标 |
| `tool` | ✅ | string | 产出工具名 |
| `severity` | ✅ | enum | `critical/high/medium/low/info` |
| `cve` / `cwe` / `cvss` | ❌ | string/number | 漏洞编号与评分（无则省略） |
| `title` / `description` | ✅ | string | 人读摘要与详情 |
| `evidence` | ✅ | string | 支撑证据片段（原始工具输出摘录） |
| `remediation` | ❌ | string | 修复建议 |
| `confidence` | ✅ | number | 0~1，部件对该发现的置信度 |
| `mitre` | ❌ | string[] | MITRE ATT&CK 技术映射 |
| `timestamp` | ✅ | string | ISO8601 UTC |

**上报方式**：部件执行完毕，大脑从 `/status`、`/history` 或事件流中回收输出 → 大脑解析为结构化 Finding → 落库（部件本身不落库，只上报原始输出/草稿）。

## 4. Report（报告）

```json
{
  "task_id": "T20260813-0001",
  "domain": "pentest",
  "summary": "对 10.0.0.5 的渗透测试发现 3 个高危问题，其中 1 个可被利用",
  "findings": ["F-T20260813-0001-001", "F-T20260813-0001-002"],
  "verdict": "real_threat",
  "confidence": 0.87,
  "mitre": ["T1190"],
  "appendix": {
    "thought_chain": "...",
    "compliance": {"level": "等保2.0-三级", "passed": false}
  }
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `task_id` | ✅ | 关联任务 |
| `domain` | ✅ | 报告域（可 `all` 表示跨域综合报告） |
| `summary` | ✅ | 摘要（人读） |
| `findings[]` | ✅ | 引用 Finding id 列表（报告可追溯） |
| `verdict` | ✅ | `real_threat` / `false_positive` / `pending_review` |
| `confidence` | ✅ | 大脑综合置信度 0~1 |
| `mitre[]` | ❌ | 综合攻击链的 ATT&CK 映射 |
| `appendix` | ❌ | 附录：思维链、等保合规检查结果等 |

## 5. SSE 事件流（部件 → 大脑）

- 端点：`GET /events`（reasonix serve 原生，`text/event-stream`）
- 大脑**每个部件常驻一条订阅**；事件为 JSON 帧，字段沿用 reasonix 原生事件，大脑侧按 `task_id`/事件类型路由
- 关键点：**/events 是实例级全局广播**（这正是"一部件一实例"的原因）——大脑给每个部件各开一条订阅，事件天然按部件隔离
- 事件流中需要人工审批的工具调用（`tool_approval_mode=ask`）会推送审批请求，大脑经 `POST /approve` 应答

## 6. 大脑 ↔ reasonix serve 的映射（HTTP 层）

reasonix serve 的原生 API 与统一协议的对应：

| 统一协议动作 | reasonix 端点 | 说明 |
|---|---|---|
| 下发任务 | `POST /submit` | body `{"input": "<TaskMessage 序列化文本>"}`；`input` 以 `!` 开头会被拒绝（403），禁止 shell 前缀 |
| 流式接收 | `GET /events` | SSE，常驻订阅 |
| 轮询状态 | `GET /status` | 运行状态/余额/用量 |
| 审批应答 | `POST /approve` | 审批工具调用 |
| 取消任务 | `POST /cancel` | 超时/人工中止 |
| 切换模型 | `POST /submit` 带 `/model <ref>` | 运行时切模型 |
| 新建会话 | `POST /new` | 每任务独立会话，防串扰 |

**TaskMessage → input 的序列化约定**（大脑侧实现，部件侧解析约定）：

```
任务 {task_id} ({domain}): {任务描述}
目标: {target}
参数: {params 的 JSON}
可用工具: {tools 列表}
上下文: {context.evidence_summary}
```

部件收到后按此格式解析；**严禁把整包 TaskMessage 当提示词原文丢给模型**（防止 prompt 注入面扩大）。

## 7. 错误与重试

| 场景 | 大脑行为 |
|---|---|
| `POST /submit` 返回非 2xx | 指数退避重试 ≤3 次，仍失败 → 任务置 `failed`，走降级路径（备选部件/人工） |
| SSE 断连 | 自动重连（15s 心跳保活），断连期间事件不丢失（部件侧有会话存档） |
| 审批超时（如 5 分钟无人确认） | 默认拒绝该工具调用，任务标记 `pending_approval` |
| 部件崩溃 | 通过 `POST /resume` 恢复会话，或按 `params.max_steps` 重发 |

## 8. 兼容性与版本

- 协议版本号放在 TaskMessage/Finding 的 `"proto_ver": 1`（可选字段），大脑与部件校验
- 新增字段必须**向后兼容**（旧字段不删、新字段可选）；不兼容变更需升级 `proto_ver` 并全量回归
- 本文档为协议唯一权威来源，代码实现与之冲突时以本文档为准并修代码
