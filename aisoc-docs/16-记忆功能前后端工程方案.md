## 0. 一页纸结论

记忆功能要解决的核心问题只有一个：**让模型在新会话里也能用到跨会话沉淀的信息**。

当前链路中：

- ✅ **已具备**：登录鉴权、会话/消息落 PostgreSQL（`chat/stream` 带 `conversation_id` 即双写消息）、前端记忆面板 UI 骨架、SSE 统计/引用帧的渲染管线。
- ❌ **缺口在后端**：大脑没有任何 `/api/memory*` 路由、没有 `memory_entries` 表、对话时不做记忆召回与注入、`/api/rag/search` 现存代码报错（`'str' object is not callable`）。
- ❌ **缺口在前端**：从不传 `conversation_id`、记忆面板数据来自浏览器 localStorage（全局键、不按用户隔离、且不注入对话）、记忆开关不通知后端、未接 `/api/conversations` 服务端历史。

**建议分三期落地，M1 即可拿到完整可用的最小闭环（手动记住 → 新会话自动召回）**，不需要等向量库就能交付。

### 1.3 必须先统一的边界认知：三层"记忆"不是一回事

```
① 工作记忆（本轮上下文）      已由模型 context window 天然提供，无需新建
② 会话记忆（同一会话历史）    后端已具备：messages 表 + 摘要字段，前端只需传 conversation_id 并接历史 API
③ 长期记忆（跨会话、用户级）  本方案主体：memory_entries + 检索注入，桌面端的 MEMORY.md 文件记忆不参与 Web 链路
```

前端面板里原有的 docs/facts（reasonix 文件记忆）属于**部件侧执行期记忆**，仅在 Wails 桌面壳内有效；Web 端以本方案的服务端记忆为准，两者不做数据互通。

## 2. 目标架构（对齐 doc-15 Part B）

```
浏览器                    大脑 :6657                         PostgreSQL
──────                    ───────────                        ──────────
Composer ──chat/stream────▶ ① 鉴权取 user_id
  {conversation_id,        ② 取工作记忆(messages 最近N条)
   use_memory:true}        ③ embed(用户问题) ──向量召回──▶ memory_entries (pgvector)
                           ④ 取 user_profiles 注入 system prompt
                           ⑤ 拼三层上下文 → LLM/部件
SSE ◀── memory_retrieved   ⑥ turn_done 后异步：
      memory_stored           LLM 抽取关键信息 → embed → 写 memory_entries
◀── assistant text                                  conversations / messages（已具备）
MemoryPanel ──GET/POST──▶ /api/memory（CRUD，手动记住/忘记/搜索）
            ──GET/PUT──▶ /api/memory/profile（画像查看/编辑）
Settings    ──PATCH────▶ /api/settings/runtime（记忆总开关）
```

**分层原则（避免把可选能力当主链路）**：

- **主链路（M1 必做）**：工作记忆（已具备）+ 手动长期记忆 + 关键词/向量召回注入。
- **增强链路（M2）**：自动提取、用户画像。
- **维护链路（M3）**：艾宾浩斯衰减、相似记忆合并、定时任务、文档记忆（docs）。

## 3. 后端工作包（B0 – B8）

> 约定：所有记忆接口挂与 `/api/conversations` 相同的 Bearer 鉴权中间件，**一律从 token 解析 user_id，禁止前端传 user_id**（防越权）。响应体沿用 conversations 的 camelCase 风格；`chat/stream` 请求体继续沿用既有 snake_case，不做改名。

### B0【前置盘点】向量基础设施确认（0.5 人日）

请后端先确认并回传结论，决定 M1 是否需要向量检索：

1. PostgreSQL 是否已有 pgvector 扩展（`SELECT * FROM pg_extension WHERE extname='vector';`）。
2. 排查 `/api/rag/search` 现有代码：embedding 用的什么（本地模型 / OpenAI 兼容接口）、表是否已存在、`'str' object is not callable` 的具体位置。
3. 若已有可复用 embedder，M1 直接走向量召回；若没有，M1 先用 **keywords 精确匹配 + PostgreSQL 全文检索（pg_trgm/tsvector）** 闭环，embedding 推迟到 M2，表结构预留 `embedding` 列即可。

### B1【M1】DDL：长期记忆表（0.5 人日）

按 doc-15 §7.1 建 `memory_entries`，两处务实调整：

- `embedding vector(N)` 列允许 NULL（M1 无 embedder 时不写，M2 补齐后回填），向量索引在 M2 再建。
- 增补 `updated_at TIMESTAMPTZ`、`scope VARCHAR(16) NOT NULL DEFAULT 'global'`（`global` 用户级 / `project` 项目级，预留），与现有 UI 的 scope 概念兼容。
- 先建普通索引：`(user_id, status, type, importance DESC)`、`GIN(keywords)`。

迁移脚本随版本发布执行；`users` 外键 `ON DELETE CASCADE`（销号即清记忆）。

### B2【M1】记忆 CRUD API（1.5 人日）

实现 doc-15 §10.1-10.3 并补齐 PATCH 与手动写入的服务端默认值：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/memory?type=&q=&minImportance=&page=&pageSize=` | 列表+分页+过滤+总数；`q` 同时匹配 content 与 keywords（M1），M2 增加语义检索并在响应标注 `matchedBy: "vector"\|"keyword"` |
| POST | `/api/memory` | 手动记住：`{content, type?, importance?, keywords?}`；服务端强制 `source='user_marked'`、`importance>=80`、生成 embedding（若可用） |
| PATCH | `/api/memory/{id}` | 编辑 content/importance/keywords，重新 embed |
| DELETE | `/api/memory/{id}` | 显式遗忘：`status='forgotten'`（软删除，保留审计） |
| POST | `/api/memory/forget-all` | 清空当前用户全部记忆（二次确认在前端做） |

**响应条目字段（前端直接消费，camelCase）**：

```json
{
  "id": "uuid", "content": "用户偏好使用 nmap 做端口扫描",
  "type": "preference", "importance": 100,
  "keywords": ["nmap"], "source": "user_marked",
  "createdAt": "ISO8601", "updatedAt": "ISO8601",
  "lastAccessedAt": "ISO8601", "accessCount": 0
}
```

错误码复用现有风格：`401 UNAUTHORIZED` / `404 NOT_FOUND`（记忆不属于本人也返回 404，不暴露存在性）/ `422 VALIDATION_ERROR`（content 空或超长，建议上限 2000 字）。

### B3【M1】对话链路集成：召回注入 + 新 SSE 帧（2 人日，核心）

1. **`conversation_id` 处理**：已登录用户必传（缺失时大脑自动创建 conversation 并在首个 SSE 帧回传 id，见下），消息持久化已具备，无需重做。
2. **检索时机**：在拼装上下文时（任务意图/普通问答都走），用当前用户消息检索该用户 `status='active'` 的记忆，top_k=5、min_importance=40（走 doc-15 §7.2；M1 无向量时退化关键词检索）。
3. **注入格式**：在 system prompt 中以固定段落注入，例如 `[用户长期记忆]\n- ...`，与工作记忆、摘要分区明确，便于模型区分时效。
4. **触达反馈（touch）**：被命中的记忆更新 `last_accessed_at/access_count`。
5. **SSE 新增帧（在首条 reasoning 之前下发）**，命名与现有 kind 风格一致：

| kind | payload | 用途 |
|---|---|---|
| `conversation_bound` | `{conversationId}` | 大脑自动建会话时回传 id，前端据此更新本地 tab |
| `memory_retrieved` | `{entries: [{id, content, type, importance, matchedBy}]}`, `injected: true` | 透明展示"本轮参考了哪些记忆" |
| `memory_stored` | `{count, entries: [{id, content, type}]}` | M2 自动提取后回执；M1 手动写入不经过流 |
| `profile_applied` | `{profile: {...}}` | M2 使用 |

6. **请求体新增开关**（ChatRequest 扩展，全部可选默认 true）：`use_memory`（长期记忆召回）、`use_profile`（画像注入）。已有的 `use_rag` 语义需明确：建议 `use_rag` 专指外部知识库（部件文档 RAG），`use_memory` 专指用户长期记忆，二者不要混用。

### B4【M2】异步记忆提取管线（2 人日）

按 doc-15 §6.4 + §7.3：

- 触发点：SSE `turn_done` 之后异步任务（建议 BackgroundTasks / 独立 worker，**绝不阻塞回答**）。
- 输入：本轮完整消息；输出 JSON 数组 `{content, type∈fact|preference|goal|entity|skill, importance, keywords}`。
- 写库前做**去重/幂等**：与同用户现有 active 记忆算相似度（向量 cosine > 0.9 或 content 归一化精确匹配）→ 命中则更新 importance/last_accessed，不新增；提取结果为空不写。
- 完成后向同一 SSE 流补发 `memory_stored`（若连接已断则只落库，前端下次开面板可见）。
- 每轮提取条数上限（建议 5 条）防刷库；工具原始输出不参与提取。

### B5【M2】用户画像（1 人日）

按 doc-15 §8 建 `user_profiles`，实现 `GET/PUT /api/memory/profile`（§10.4/10.5），并在 B3 的 system prompt 拼装中按 `use_profile` 注入。PUT 支持部分字段 + version 乐观锁；自动归纳任务可复用 B4 的异步管线。

### B6【M3】衰减 / 遗忘 / 合并（1.5 人日）

按 doc-15 §9：APScheduler 每日任务重算 `decay_score`、低分归档、相似聚类合并（threshold 0.85）、删除对话时关联记忆衰减 ×0.1。**M1/M2 不做也不影响主功能**，但表字段需在 B1 一次建好，避免二次迁移。

### B7【M1】修复 RAG + 设置开关生效（0.5 人日）

1. 修复 `/api/rag/search` 的 `'str' object is not callable`；参数对齐 OpenAPI（`q` 必填、`k` 可选），前端不会再传 `top_k`。
2. `GET/POST /api/settings/runtime` 的 `memoryCompilerEnabled` 需真正被对话管线读取（或统一改名为 `memoryEnabled` 并同步前端，二选一但需告知）。

### B8【M1】鉴权收口（0.5 人日）

安全前置：实测 `/api/tasks` 不带 token 也返回 200。请排查并把 `/api/tasks*`、`/api/findings`、`/api/data/*`、`/api/reports/*` 等数据接口全部挂 Bearer 鉴权 + 用户隔离（记忆功能依赖"任务/会话属于哪个用户"的可靠边界，否则记忆提取会串用户）。

**后端工作量合计：M1 约 7 人日（含 B0 盘点）、M2 约 3 人日、M3 约 1.5 人日。**

## 5. 端到端时序（M1 验收主流程）

```
1. 用户登录 → 前端持有 Bearer token
2. 新建会话首条消息：
   前端 POST /api/conversations → conversationId
   前端 POST /api/chat/stream {message, conversation_id, use_memory:true}
3. 大脑：鉴权→检索该用户记忆→（无命中）→LLM 回答→落 messages→SSE turn_done
4. 用户打开记忆面板，手动"记住"：POST /api/memory {content:"靶场授权域名是 demo-campus.edu.cn",type:"fact"}
5. 用户另开一个新会话再问：大脑检索命中 →
   SSE 先推 memory_retrieved（含该条）→ 回答中正确使用授权域名
6. 前端面板刷新：该条 accessCount=1、lastAccessedAt 更新
7. 用户点"忘记"→ DELETE → 后续会话不再召回
```

## 7. 风险与决策点（需双方确认后开工）

1. **Embedding 选型**：优先本地 `bge-small-zh-v1.5`（512 维、无外网依赖、中文安全语料合适）；若服务器无 GPU，CPU 上单条短文本编码延迟约 20-50ms，可接受。需 B0 盘点后定。
2. **两接口语义澄清**：`use_rag`（外部知识库）vs `use_memory`（用户记忆）必须分开；`memoryCompilerEnabled` 是否改名需后端定夺并通知前端。
3. **提取成本与隐私**：每轮异步多一次 LLM 调用，建议仅在用户消息 > 一定长度且开关开启时触发；安全任务输出可能含敏感目标信息，记忆面板必须提供一键清空，且记忆严格按用户隔离。
4. **多部件域记忆是否共享**：pentest/logaudit/intel 的发现（findings）目前是任务级数据；是否把"结论级发现"自动提取为用户长期记忆，建议 M2 再议，M1 只存用户显式记住的内容。
5. **桌面端兼容**：Wails 继续走文件记忆，Web 走服务端记忆，绑定层分流，互不迁移历史数据。
6. **性能**：召回必须走索引 + 超时兜底（向量服务异常时降级为"无记忆"回答，不能阻断对话）。

## 8. 验收清单

### 后端（curl 脚本）

- [ ] 未带 token 调 `/api/memory` 返回 401；A 用户 token 访问 B 用户记忆 id 返回 404
- [ ] POST 记忆 → GET 列表可见；PATCH 可改；DELETE 后列表消失但库中 status=forgotten
- [ ] 写入记忆后开新会话提问，SSE 中先出现 `memory_retrieved` 且回答用到该内容
- [ ] 命中后 `accessCount/lastAccessedAt` 更新；`use_memory:false` 时不召回
- [ ] `/api/rag/search?q=test&k=3` 返回 200
- [ ] `/api/tasks` 无 token 返回 401
- [ ] embedding 服务宕掉时对话仍正常返回（降级不阻断）

### 前端（UI 用例）

- [ ] 发消息后刷新页面，会话与完整消息仍在（服务端历史）

- [ ] 忘记/清空后新会话不再召回
- [ ] 记忆开关关闭后对话不召回、面板禁用态正确
- [ ] 无网络/大脑 502 时面板显示错误而非白屏；Wails 桌面模式文档记忆区不受影响
